Tray/background add-on 0.1.2 validation

The user's 0.1.1 native self-check correctly refused a child still associated with a job. It failed before replacing the add-on. Version 0.1.2 replaces that direct launch path with a manual Windows Task Scheduler owner; it does not weaken a parent-job check and retry the same terminal-owned process. Direct breakaway/process-creation APIs are absent from the launch path; the legacy C# filename supplies argument quoting only.

Local checks: PowerShell parse; managed SessionHost/argument helper compilation; real PowerShell held-input/stop fixture; tray status and profile contracts; task definition/ownership model (no triggers/restart, current interactive elevated SID, no stored password, administrator-only task ACL, battery permitted, no execution timeout, duplicate-ignore policy, foreign-action/trigger rejection); installation fixture with Windows ACL/COM boundaries stubbed (injected failure rollback, install, repeat install, 0.1.0 -> 0.1.2 upgrade, remove). Core hashes, core manifest bytes, active peer, device key and recorded session remain unchanged.

Windows self-check is included and mandatory before installer changes: a temporary on-demand task launches a console-free test worker with the same scheduled bootstrap. That worker exercises held input and nested job cleanup using harmless dummy processes and the existing protected ProcessJob.cs. Probe task/files are removed afterwards. No live tunnel is started, recovered or changed by this test. The real Windows Task Scheduler/WinForms and full background VPN cannot be executed in Linux; first Windows self-check and connection remain to be observed.

The product on-demand task is created when Connect is clicked, has no automatic triggers/restart, uses current logged-in account with highest privileges and stores no password. It does not stop on battery or after the default three-day limit. Closing terminals or the tray is separate from the scheduler-owned session. Sign-out/reboot still end user processes; persistent guard recovery behavior remains unchanged. Removing a running scheduled background owner is refused until explicit recovery/disconnection.
